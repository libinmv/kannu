# Claude Code cloud sessions

Claude Code sessions that run in the cloud (claude.ai/code, or a local session moved to the cloud)
are invisible to Kannu by construction:

- Kannu's hook is installed in the user-level `~/.claude/settings.json`. A cloud session runs on
  Anthropic's VMs, which only run hooks committed to the repository's `.claude/settings.json`.
- Nothing about a cloud session is written to this Mac, and `claude agents --json` lists only
  local sessions.

The only supported path is a relay, and it is opt-in: a small hook committed to the repository
posts the session's light to an [ntfy](https://ntfy.sh) relay, and Kannu subscribes to it.

**Status:** the protocol, the script and Kannu's parser are in place and tested. The listener that
turns reports into notch cards, and the Settings section that sets this up, are not wired yet.

## Moving parts

| Piece | Where | What it does |
|---|---|---|
| The relay script | `.claude/hooks/kannu-cloud-relay.sh` in the user's repository; authoritative copy `ClaudeCloudRelaySetup.scriptSource`, mirror `scripts/kannu-cloud-relay.sh` | Runs on every Claude hook event. Does nothing unless `CLAUDE_CODE_REMOTE=true` and `KANNU_RELAY_SECRET` is set. |
| The hooks | the repository's `.claude/settings.json`, generated by `ClaudeCloudRelaySetup.hooksJSON()` | One async command per row of `AgentHookLayout.claudeHookEntries`, the table Kannu's own Claude install uses. |
| The relay key | the cloud environment's variables, and Kannu's Keychain | 64 lowercase hex characters (256 bits). Never in a repository, an agent prompt or a log. |
| The parser | `ClaudeCloudRelay` | Turns one line of ntfy's JSON stream into a report, or rejects it. Pure. |

Kannu never writes into a repository. It hands out the script and the hooks (as a prompt for the
user's own coding agent, `ClaudeCloudRelaySetup.repositoryPrompt()`, which never contains the key)
and the environment lines (`ClaudeCloudRelaySetup.environmentLines(secret:server:)`).

## Keys

Both ends derive everything from the one secret:

- topic = `"kannu-"` + the first 32 hex characters of SHA-256(`"kannu-relay-topic|"` + secret)
- signing key = SHA-256(`"kannu-relay-mac|"` + secret), 32 bytes

The relay's operator sees the topic in every request; the topic does not reveal the secret, and a
message is only accepted when it is signed with the key derived from it.

Test vector, pinned by `ClaudeCloudRelayTests` and `ClaudeCloudDocsTests`:

| | |
|---|---|
| secret | `0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef` |
| topic | `kannu-d7b0368ee423e8a461a99c07f909346f` |
| signing key | `52772e70cf00178d16274ca23a4f92ee876aee074166e4eccfe4bd6f70d5e743` |

## Message format

The script POSTs one plain-text body to `<server>/<topic>`:

```
KC1 <hex HMAC-SHA256(signing key, payload)> <payload>
```

The payload is compact JSON with sorted keys, ASCII only, at most 1024 bytes.

## What a report carries

Exactly these fields, and nothing else (`ClaudeCloudRelay.payloadKeys`):

| Field | Meaning | Values |
|---|---|---|
| `v` | protocol version | `1` |
| `kind` | marks a Kannu report | `kannu-cloud` |
| `session` | the session id (`CLAUDE_CODE_REMOTE_SESSION_ID`) | `session_…` or `cse_…`, letters and digits |
| `state` | the light's state | `idle`, `thinking`, `executing`, `awaiting_input`, `stopped`, `session_end` |
| `event` | the hook event | a Claude hook event name, or `Check` from `--check` |
| `note` | the notification kind | `permission_prompt`, `idle_prompt`, `agent_needs_input`, `agent_completed`, or empty |
| `repo` | the repository folder's name, never its path | `[A-Za-z0-9._-]`, at most 64 characters |
| `ts` | a timestamp: the session's clock, in milliseconds | strictly increasing per session |

Never sent: a prompt, a command, tool input or output, a file or a path, notification text, or
the transcript. `ClaudeCloudRelayScriptTests` plants markers in every one of those and checks that
none leaves the session.

Who sees what: the relay's operator sees the topic, the metadata above, when each report was sent,
the cloud session's outbound IP address and, when Kannu subscribes, this Mac's IP address.

## What Kannu accepts

A line becomes a report only if every check passes, in this order (`ClaudeCloudRelay.parse`):

1. The line is at most 16 KiB and is a JSON object; `open` and `keepalive` lines only mean the
   stream is alive.
2. It is a `message` for this user's topic, with the relay's receive time.
3. The body is `KC1`, a 32-byte hex MAC and a payload of at most 1024 bytes, and the MAC is valid.
4. The payload has exactly the eight keys above, each with an allowed value, a well-formed
   session id and a well-formed folder name.
5. Its `ts` is within 600 s of the relay's receive time.

A report is dated by the relay, never later than this Mac's clock, so a relay clock running ahead
cannot keep a card fresh. A `cse_` id becomes `session_`, the form claude.ai's URLs use.

Kannu keeps the newest report per session, whatever order they arrive in; a tie goes to the more
urgent state, and a replayed old report changes nothing. It remembers at most 32 sessions, and
forgets one after an hour without news.

## The light

A cloud card goes through the same ladder as a hook file (`resolveHookState`, REGRESSIONS
entries 2 and 12):

- Green lasts 360 s after the last report. The script re-sends an unchanged green every 240 s, so
  a long run stays green.
- A waiting prompt stays yellow only while Kannu's connection to the relay is healthy; without it,
  nothing says the prompt is still open, and the 5-minute clock applies. An idle notice
  (`idle_prompt`) is always on the clock, as it is for a local Claude session.
- Stopped collapses as usual; a `StopFailure` carries the "failed" verdict.
- The stale cap ends every card.

A cloud card's conversation id is `claudecloud.` + the session id. A dot never survives the local
hook's id sanitizing, so a cloud card can never merge with a local chat.

## When the script sends

ntfy.sh limits requests per IP address, and cloud sessions share Anthropic's outbound addresses;
its free tier is reported at 250 messages a day. So the script sends only when the light changes
colour, plus one refresh at most every 240 s while it stays the same. A typical turn is three to six
messages. A self-hosted ntfy server avoids the shared quota: set `KANNU_RELAY_URL` in the cloud
environment.

The script ports the rules of Kannu's main hook:

- The generic `PreToolUse` hook stays quiet for a question tool (`AskUserQuestion`,
  `ExitPlanMode`); the question's own matcher group reports it as yellow.
- A green within 2 s of a yellow from a permission request, a notification or a question does not
  replace it: a sibling tool call finishing must not hide an open prompt.
- A `SessionStart` from a compaction or a resume is skipped.
- A subagent never relights a chat that has finished.
- An interrupted tool means stopped.
- A send that fails is not remembered as sent, so the next event retries it.

Every hook is `async`, so a slow relay never holds a turn up. The script never prints (a hook's
stdout becomes part of Claude's context) and always exits 0. Its memory of what it last sent lives
in a private folder under `$TMPDIR`, which it ignores if the folder is shared or is a link.

## Checking a setup

From a cloud session's terminal:

```
bash .claude/hooks/kannu-cloud-relay.sh --check
```

It says whether it is in a cloud session, whether the session id and the key are present (never
printing the key), which relay it uses, then sends a signed test message and explains the answer:
HTTP 403 means the environment's network access does not allow the relay's host, and HTTP 429
means the relay's quota for that network is used up. On ntfy.sh it also prints the messages left
today. A test message never becomes a card.

## Limits

- The cloud environment's network access must be **Custom**, allowing the relay's host; the
  default (Trusted) allows only package registries, GitHub and cloud SDKs.
- Only single-repository sessions run repository hooks. Organisations that allow only managed hooks
  cannot use this.
- The key is readable inside the cloud VM, so a prompt injection could read it. The worst it can do
  is forge cards and read the metadata above; regenerating the key in Kannu ends it.
- Teammates' local sessions run the committed hook too; outside the cloud it is one bash test and
  an exit.

## Tests

- `ClaudeCloudRelayTests`: keys, parsing and every rejection, ordering, the session cap, cards.
- `ClaudeCloudRelayScriptTests`: the real script with a fake `curl` on PATH: what leaves the
  session, when it is sent, `--check`, and the mirror.
- `ClaudeCloudRelaySetupTests`: the hooks, the prompt and the environment lines.
- `ClaudeCloudDocsTests`: this document's field table and the consent text name exactly the
  payload's fields.
- `RegressionGuardTests`: the refresh stays inside the green window; a cloud yellow is held only
  while the relay is listening.
